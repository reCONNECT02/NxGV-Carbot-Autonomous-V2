## 01 / SETUP — Set the map, start and goals  (`#setup`)
*We load one shared course and one measured car.*

- **Input**: Course drawing + car size.
- **Process**: Set the start and two destinations.
- **Output**: One scale for every planner.

**What the V4 code actually does:** Car: 30 × 19.2 cm. Wheelbase: 21.6 cm. Lane: 30 cm. Rear-axle turning radius: editable; 40 cm default. The start and map are preloaded in V4. A real manual map/UWB calibration lap is still to implement.

**Source:** `core.js · DEFAULTS, Course`

**Feeds into:** 07 Global Route Planner, 02 Cameras + Motion + Ranges

## 02 / SENSE — Give each sensor a job  (`#sensors`)
*Three cameras see the road. Other sensors support them.*

- **Look**: Front + two rear-quarter cameras.
- **Feel motion**: Wheel distance + IMU heading.
- **Measure position**: LiDAR checks obstacles. UWB locates coarsely.

**What the V4 code actually does:** V4 renders three 192 × 144 camera feeds at 8 Hz. UWB samples at 5 Hz. LiDAR scans about every 0.18 s. Camera mounts are provisional. These rates are simulator settings, not RDK X5 measurements.

**Source:** `scene.js · capture, lidar / vehicle.js · Sensors`

**Feeds into:** 03 Warp → Stitch → Road Mask, 05 Smooth Local Position, 06 Coarse Uwb-Aided Position, 14 Safety Checks

## 03 / SENSE — Turn three views into road  (`#vision`)
*We warp each camera into the same top-down space.*

- **Input 1**: Front camera.
- **Input 2**: Left rear-quarter camera.
- **Input 3**: Right rear-quarter camera.
- **Warp + stitch**: Choose the stronger view at each cell.
- **Seed**: Start from seen road near the car.
- **Grow**: Keep the connected dark-road region.

**What the V4 code actually does:** Projection uses provisional pinhole calibration and a flat local-ground assumption. The stitch chooses one camera per cell; it does not average all three. Dark neutral pixels become road; bright pixels become paint. Growth uses four touching neighbours. These camera and mask images were generated by V4.

**Source:** `perception.js · projectionMap, process, support`

**Feeds into:** 04 Recent Local Memory, 05 Smooth Local Position, 09 Corridor + Branch Check

## 04 / SENSE — Remember what just disappeared  (`#memory`)
*We keep recent road edges in a fixed local frame.*

- **See**: Save road, paint and the time.
- **Move**: The car moves. Saved cells stay put.
- **Reuse briefly**: Use recent edges outside the camera view.
- **Expire**: Old or uncertain cells stop guiding motion.

**What the V4 code actually does:** Driving uses observations up to 2–3 seconds old, with a motion-based uncertainty limit. The display can show 25 seconds. Bay-edge lookup can use 24 seconds during parking. LiDAR scans are separate; they are not accumulated into this grid.

**Source:** `vehicle.js · LocalMemory / guidance.js · evidence`

**Feeds into:** 09 Corridor + Branch Check, 11 Parking Planner, 12 Recovery Planner

## 05 / LOCATE — Keep a smooth local position  (`#pose`)
*We use wheels, IMU and seen edges for precise driving.*

- **Predict**: Move the estimate using wheel + IMU data.
- **Compare**: Match camera edges with nearby map edges.
- **Correct**: Remove local drift with small corrections.

**What the V4 code actually does:** Position here means location plus heading. Camera matching corrects translation; simulated IMU heading supplies orientation. Straight edges mainly constrain sideways error. Matching pauses on steep pitch and during parking. V4 is prior-map-aided; it is not full visual SLAM.

**Source:** `vehicle.js · Estimator.update, visualUpdate`

**Feeds into:** 04 Recent Local Memory, 06 Coarse Uwb-Aided Position, 09 Corridor + Branch Check, 11 Parking Planner

## 06 / LOCATE — Let UWB help in the background  (`#globalpose`)
*We keep noisy UWB away from the steering position.*

- **Input**: Scattered UWB measurements.
- **Process**: Reduce the weight of noisy fixes.
- **Output**: A separate coarse course position.

**What the V4 code actually does:** The violet estimate includes UWB. The yellow local estimate never receives a UWB position jump. Distinctive visual geometry also helps the coarse estimate. The confidence values are approximate model indicators. The orange cloud here is a synthetic illustration at 20 cm σ per axis.

**Source:** `vehicle.js · Estimator.update, globalPose`

**Feeds into:** 09 Corridor + Branch Check

## 07 / PLAN — Global planner: choose the road route  (`#global`)
*We connect clockwise checkpoints to each destination.*

- **Input**: Prior map + start + destinations.
- **Process**: Search car-like paths between checkpoints.
- **Output**: A route to the traffic-light stop.

**What the V4 code actually does:** V4 precomputes two directed routes from configured checkpoints. It checks the whole nominal body and turning radius. It does not compare every possible route or choose exits from UWB alone. Global road approach ends at the parking handoff; local parking starts there.

**Source:** `core.js · buildMission, hybridPlan`

**Feeds into:** 08 Mission Logic, 09 Corridor + Branch Check

## 08 / PLAN — Mission logic: choose what happens now  (`#mission`)
*We choose the active route, behaviour and motion source.*

- **Round one**: Start bottom-right. Drive clockwise to the light.
- **At the light**: Stop. Continue only after observed green.
- **Round two**: Continue clockwise. Reach the bay and park.

**What the V4 code actually does:** The state machine chooses ROAD, PARKING or RECOVERY. Seen red lights and closed gates cause holds. Recognition is ideal only when visible and not occluded. Ramp/bump speed zones use the prior map; V4 does not implement a separate sign detector for every challenge.

**Source:** `app.js · step, transition`

**Feeds into:** 09 Corridor + Branch Check, 11 Parking Planner, 12 Recovery Planner, 13 Path → Motion Request

## 09 / PLAN — Find the lane we should follow  (`#corridor`)
*We combine the chosen branch with the road we see.*

- **Input**: Seen road edges + active route.
- **Process**: Find the middle between paired edges.
- **Output**: A small correction to the local guide.

**What the V4 code actually does:** The guide keeps the route’s useful offset through tight turns. The car need not sit on the exact geometric centreline. The route selects the exit; local road evidence checks the opening. A course-location conflict holds. Missing local visibility may trigger checked recovery.

**Source:** `guidance.js · corridor, branchCheck`

**Feeds into:** 10 Local Path Planner

## 10 / PLAN — Local planner: choose the next movement  (`#local`)
*We pick the lowest-cost candidate that passes the checks.*

- **Input**: Current pose + camera-conditioned guide.
- **Try**: Predict nine short steering paths.
- **Check**: Test body clearance, road evidence and obstacles.
- **Choose**: Grey = tried. Blue = selected.

**What the V4 code actually does:** Runs at 5 Hz. Nine lateral alternatives follow the chosen branch; they do not enumerate every roundabout exit. If all strict paths fail, V4 tries nine more with the adjustable 0–5 cm paint allowance. Boundary crossings still count. Persistent failure can start recovery. These candidate drawings come from a V4 run.

**Source:** `local-planner.js · candidates, rollouts`

**Feeds into:** 13 Path → Motion Request, 12 Recovery Planner

## 11 / MANOEUVRE — Parking planner: compute the manoeuvre  (`#parking`)
*We plan into the observed bay. We do not replay motion.*

- **Input**: Handoff pose + camera-supported bay.
- **Search**: Try forward/reverse car-like connections.
- **Execute**: Track the path. Stop before each gear change.
- **Finish**: Check the whole car is inside.

**What the V4 code actually does:** Reeds–Shepp curves use forward and reverse arcs. V4 tries a 15/12/8 cm docking straight, then other connections and a bounded hybrid fallback. Up to 48 family transforms are evaluated per start/goal pair; fewer valid curves may result. This is a computed geometry example, not a recorded parking result.

**Source:** `core.js · parkingPlan / reeds-shepp.js · candidates / app.js · transition`

**Feeds into:** 13 Path → Motion Request, 14 Safety Checks

## 12 / MANOEUVRE — Recovery planner: make room, then rejoin  (`#recovery`)
*We plan the way back before reversing.*

- **Stuck**: No usable forward movement.
- **Search**: Brake. Check rear road and LiDAR.
- **Reverse**: Back up along a checked short path.
- **Change gear**: Stop. Drive forward towards the route.
- **Rejoin**: Return control to the lane planner.

**What the V4 code actually does:** The search tries up to five future route poses. A recovery starts in reverse, then changes once to forward. Default planned reverse limit: 20 cm. Speed: 3 cm/s. It rescans if no route fits. Obstacles, stale sensors and emergency stops still prevent motion. The sequence is a computed example using V4’s search with synthetic rear-road evidence. Reverse recovery and paint tolerance are training overrides, not new competition permissions.

**Source:** `recovery.js · search, Recovery.request`

**Feeds into:** 13 Path → Motion Request, 14 Safety Checks

## 13 / ACT — Turn the path into a request  (`#tracker`)
*We aim at a nearby path point, then ask for motion.*

- **Input**: Selected path + local position.
- **Process**: Calculate steering towards the nearby target.
- **Output**: A speed request and a steering request.

**What the V4 code actually does:** The tracker uses a nearby look-ahead point. Limits come from the wheelbase and turning radius. It handles forward/reverse direction and stopped gear changes. V4 simulates actuator response; the real response still needs measurement.

**Source:** `vehicle.js · Controller.update / app.js · step`

**Feeds into:** 15 One Command Owner

## 14 / ACT — Safety: decide whether motion is allowed  (`#safety`)
*A valid path never overrides a safety stop.*

- **Check freshness**: Are camera and motion data recent?
- **Check clearance**: Is the pose usable? Is the path blocked?
- **Output**: Pass motion, or request a stop.

**What the V4 code actually does:** Camera age above 0.45 s stops motion. Local uncertainty, physical contact, tunnel clearance and unresolved route identity also cause holds. Recovery can solve a planning deadlock; it cannot bypass these limits. Thresholds are simulator settings.

**Source:** `app.js · safety checks / recovery.js · obstacle checks`

**Feeds into:** 15 One Command Owner

## 15 / ACT — Command owner: one final writer  (`#owner`)
*Every block asks. Only one owner commands the car.*

- **Input**: One active motion request + safety state.
- **Priority**: Safety stop → stale-request stop → active request.
- **Output**: One motor/steering command and a visible winner.

**What the V4 code actually does:** V4’s mission code selects the active source. The owner then checks safety and the 200 ms request age. It does not implement a queue of competing ROS publishers. ROAD, PARKING, RECOVERY, WATCHDOG and SAFETY STOP are visible on the dashboard.

**Source:** `vehicle.js · arbitrate / app.js · step`

**Feeds into:** 16 Vehicle + New Observations

## 16 / ACT — Move, observe, repeat  (`#vehicle`)
*Each command changes the next sensor readings.*

- **Command**: Apply speed and steering.
- **Motion**: Simulate response and ground shape.
- **Feedback**: Render new cameras. Sample sensors again.

**What the V4 code actually does:** The physics state renders sensors and checks errors. Green truth is for assessment, not position input to the planner. Motion uses simplified steering and speed response. The nominal body collider does not certify mast clearance, tyre grip or suspension. The measured overheight mast still needs a physical fix.

**Source:** `vehicle.js · Plant / scene.js · WorldView / app.js · assess`

**Feeds into:** 02 Cameras + Motion + Ranges
